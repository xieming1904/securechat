## 1. 一句话总结

消息、附件、头像、群名、表情回应、投票、草稿和个人数据，都在浏览器里加密后才发给服务器，服务器保存的是看不懂的密文。
服务器**看不到内容**，但**看得到元数据**：谁和谁在聊、什么时候、发了多少条、文件有多大。
服务器也**改不了**成员名单、群设置和别人的消息，改了客户端会报警。

## 2. 威胁模型

### 防得住的

| 攻击者 | 能做什么 | 密聊的应对 |
|---|---|---|
| 拿到数据库或备份的人（包括服务器被入侵、云盘备份泄露） | 读所有表 | 只有密文。登录用 OPAQUE，数据库里没有能离线暴力破解的密码哈希。身份密钥的备份由 OPAQUE 导出密钥加密，没和服务器完成一次 OPAQUE 就解不开。 |
| 恶意或被入侵的服务器（主动攻击） | 篡改、伪造、重放、回退数据 | 消息逐条签名；成员变更是签名链；群设置由管理员签名，带版本号；头像密钥签名。检测到异常时显示红色警告，并停止发送。 |
| 网络上的窃听者 | 看流量 | HTTPS；另外内容本身已经端到端加密。 |
| 没被放行的陌生人 | 扫描、爆破 | IP 准入：没放行的 IP 连登录页都看不到。访问密码失败会自动封禁；登录、两步验证、恢复词都有尝试上限。 |
| 捡到你电脑的人 | 打开浏览器 | 可选的本机应用锁（PIN）、隐私屏；可以在另一台设备上远程让它下线。 |

### 防不住的

- **你自己的设备被控制**（木马、恶意浏览器扩展）。端到端加密只保护传输和存储，终端被控制时无效。
- **服务器下发恶意的网页代码。** 网页应用每次打开都从服务器加载代码。控制了服务器的人可以换成会偷密钥的代码。这是所有网页版端到端加密的共同弱点（Telegram / WhatsApp 网页版也一样），见 [8. 已知限制](#8-已知限制)。
- **聊天里的人把内容泄露出去**（截图、转发、导出）。
- **元数据分析**：服务器知道谁和谁、什么时候通信。
- **身份密钥泄露后解密普通聊天的历史消息**：普通聊天没有前向保密。需要前向保密时请用「私密对话」（v0.8），见 [3.5](#35-私密对话v08) 和 [前向保密设计](前向保密设计.md)。

## 3. 密钥与加密

所有密码学操作都用 libsodium（`libsodium-wrappers-sumo`），不自己实现算法。

### 3.1 账号与登录

| 用途 | 做法 |
|---|---|
| 登录 | **OPAQUE**（`@serenity-kit/opaque`）。服务器从头到尾拿不到密码，也拿不到能离线爆破的哈希。 |
| 恢复词 | 24 个词，同样作为一个独立的 OPAQUE 凭据注册。 |
| 身份密钥 | 每个账号一对 **Ed25519**（签名）+ 一对 **X25519**（加密），在注册时于浏览器生成。 |
| 身份密钥备份 | 用 OPAQUE 导出密钥派生出的密钥加密（XChaCha20-Poly1305），分别以密码和恢复词各存一份。换设备登录时下载、解密。 |
| 本机保存 | 身份密钥在浏览器里用**不可导出**的 AES-GCM 密钥（WebCrypto）包裹后存进 IndexedDB。 |
| 两步验证 | 通行密钥（WebAuthn）或 TOTP 验证器，外加 10 个一次性恢复码。 |

### 3.2 聊天密钥

- 每个聊天有一把 32 字节的随机**聊天密钥**，按「纪元（epoch）」编号。
- 分发：聊天密钥用 `crypto_box_seal` 分别封给每个成员的 X25519 公钥，再由分发者用 Ed25519 签名（签名覆盖：聊天、纪元、成员版本、接收者、分发者）。
- 接收方检查两件事：签名有效；分发者在那个成员版本里确实是成员。
- **换密钥**：
  - 有人加入或被移除时，换密钥和成员变更是**原子**的，一次请求完成。被移除的人拿不到新密钥。
  - 群密钥用满 7 天或 1000 条消息后，下一个打开这个聊天或发消息的成员会自动更换（v0.8 起打开时就换，不用等到发消息）。
  - 新成员只拿到加入之后的密钥，看不到加入前的消息。

### 3.3 消息与附件

| 内容 | 做法 |
|---|---|
| 消息 | JSON → 填充到 256 字节的倍数（隐藏确切长度）→ XChaCha20-Poly1305。AAD 绑定聊天、纪元、发送者和发送方生成的消息 ID（`clientMsgId`）。服务器给的顺序号不在 AAD 里，所以服务器能扣下或打乱消息，但改不了内容。发送者再对「nonce + 密文 + AAD」做 Ed25519 签名。 |
| 附件 | 每个文件一把随机密钥，`crypto_secretstream_xchacha20poly1305` 分块加密（大文件边读边加密，最大 2 GB）。文件密钥放在消息里，随消息一起加密。 |
| 群名、群设置、公告 | 用聊天密钥加密；群设置由管理员签名，带递增版本号。 |
| 表情回应、投票 | 用聊天密钥加密并签名，服务器只知道「某人对某条消息做了回应 / 投了票」。 |
| 头像 | 图片用随机密钥加密。个人头像的密钥按聊天分别加密并签名，只发给聊天伙伴；群头像密钥放在管理员签名的群设置里。 |
| 个人数据（备注、收藏、贴纸、分组、同步设置） | 用只有自己知道的密钥加密（加密保险箱），服务器只看到条数和大小。 |
| 通话 | WebRTC（DTLS-SRTP）端到端加密。信令用聊天密钥加密并签名，防重放。可选「只走 TURN 中转」，对方看不到你的 IP。 |
| 导出存档、个人数据备份 | 口令经 Argon2id 派生密钥后加密。 |

### 3.4 安全码

两人的 Ed25519 公钥按顺序拼接后做 BLAKE2b 哈希，显示为 12 组 5 位数字和二维码。当面核对一致，就排除了中间人。对方密钥变化时，「已验证」标记自动消失，并显示提醒。

### 3.5 私密对话（v0.8，v0.9 补充通话）

| 项目 | 做法 |
|---|---|
| 设备密钥 | 每个登录的浏览器是一台「设备」，有自己的 Ed25519 + X25519 密钥，由账号密钥签发证书。另有每周更换的签名预密钥，以及一次性预密钥。 |
| 建立会话 | X3DH（Signal 规范）。先核对对方账号密钥没有变过（安全码没有变更），再验证证书链：账号 → 设备 → 签名预密钥。 |
| 收发 | 双棘轮（Double Ratchet），带头部加密。每条消息一把一次性密钥，用完即删；每次往返换一次 DH 密钥，被攻破后能自愈。 |
| 服务器 | 只转交密文，设备确认收到后立即删除，最长保留 14 天；从不进入聊天历史。 |
| 本机 | 密钥和消息用这台浏览器不可导出的 AES-GCM 密钥加密存在 IndexedDB。多个标签页之间用 Web Locks 保证棘轮状态不分叉。退出登录或被远程下线时全部删除。 |
| 附件 | 用一次性密钥加密后上传，服务器上保留 14 天后删除。 |
| 通话（v0.9） | 发起方生成一把只用于这次通话的信令密钥，和通话邀请（SDP）一起经双棘轮发给对方那台设备；之后的应答和 ICE 用这把密钥加密、账号密钥签名，通过普通中转发送。其他设备收不到密钥，不会响铃。媒体本身是 DTLS-SRTP。邀请超过 60 秒就作废。 |
| 安全码 | 由两台设备的证书计算，只属于这一对设备。 |
| 测试 | 协议有独立参考实现的逐字节对照测试，发布前做了专门的密码学审查。 |

私密对话只存在于两台设备上：换设备、清除浏览器数据后无法恢复，其他设备上也看不到。

## 4. 服务器能看到什么

| 服务器看得到 | 服务器看不到 |
|---|---|
| 用户名、昵称、个人简介（明文，用于搜索用户） | 消息、附件、语音的内容 |
| 谁和谁有聊天、群里有哪些成员 | 群名、群公告、群设置 |
| 每条消息的发送者、时间、所在聊天、密文大小（填充后） | 头像图片 |
| 附件的数量和大致大小（v0.9 起补齐到 Padmé 档位，看不出准确大小；超过 90 MB 的大文件不补齐） | 表情回应是哪个表情、投票投了哪项 |
| 已读到第几条（已读回执） | 备注名、收藏、贴纸、聊天分组、置顶和归档 |
| 谁在线（可以隐藏；v0.9 起也可以「模糊显示」：别人看到的上线、下线时间有随机延迟，但服务器自己知道准确时间） | 通话的音视频内容 |
| 谁对哪个聊天开了免打扰（为了不发推送） | |
| 私密对话：哪两台设备之间在传消息、什么时候、多大（转交后即删除） | 私密对话的内容、附件、阅后即焚设置 |
| 谁在和谁通话、通话多长；走 TURN 时看得到双方 IP | 密码、恢复词 |
| 登录设备的 IP、浏览器类型、最后活跃时间 | 身份私钥 |
| 访问验证日志（IP，默认保留 90 天） | |
| 开启链接预览时：你预览的网址 | |

**推送通知**：推送内容只有「有新消息」，不含发送者和内容。推送服务商（Google、Apple、Mozilla）只知道某个设备收到了一条通知。

**错误报告**（v0.7）：页面出错时，发给服务器的只有错误类型、错误说明的开头（遇到引号或换行就截断，只保留英文字母、数字和常见符号）和代码位置；不带账号、会话，也不记录 IP。可以在设置里关闭。

**服务器日志**（v0.7）：默认不再逐条记录请求，所以日志里不会有每个访问者的 IP 和网址，只记录错误。系统日志最多保留 500 MB / 30 天。

## 5. 防篡改：签名能保证什么

| 服务器可能的篡改 | 客户端的检测 |
|---|---|
| 伪造或修改一条消息 | 签名验证失败，这条消息不显示。 |
| 把消息挪到别的聊天或纪元 | AAD 不匹配，解密失败。 |
| 偷偷往群里加人 | 成员名单必须是签名链的结果，对不上就显示「成员列表与签名记录不一致」并停止发送。 |
| 用旧版本成员名单撤销「移除成员」 | 成员版本只增不减，发现回退就报警。 |
| 改群名、阅后即焚时长，或回退到旧设置 | 群设置有管理员签名和递增版本，发现就显示警告。 |
| 替换某人的公钥（中间人） | 安全码改变，「已验证」标记消失，并提醒核对。 |
| 换头像、回退旧头像 | 头像密钥有签名和版本号。 |
| 重放通话信令 | 信令带时间戳并签名，超过 5 分钟的拒收；5 分钟以内，同一个页面对同一条信令只接受一次（v0.8）。 |
| 冒充私密对话的对方设备 | 设备证书由对方账号密钥签发；对方账号密钥变更后，在重新核对安全码之前拒绝私密对话。 |
| 转走别人设备的私密消息队列 | 注册设备时必须用设备私钥签名，证明持有这台设备。 |

## 6. 设备与会话

- 同一个账号的所有设备使用同一套身份密钥。
- **扫码登录**：新设备生成一次性密钥对。旧设备核对 6 位码后，把身份密钥用 `crypto_box_seal` 封给这个一次性密钥，服务器只转交密文。
- 会话令牌只以哈希形式存在服务器，Cookie 设为 HttpOnly、SameSite=Strict，线上环境加 Secure（`COOKIE_SECURE=0` 只用于本机测试）。
- **敏感操作**（首次开启两步验证、注销账号）要求这次登录「最近输入过密码」；扫码登录的设备必须先输入一次密码。
- 新设备登录时，其他设备会收到提醒，可以一键让它下线。
- 找回密码（恢复词）后，所有旧会话都会失效。

## 7. 服务器侧的防护

| 项目 | 做法 |
|---|---|
| 访问控制 | IP 准入（白名单、访问密码、邀请、审批），自动封禁，WebSocket 同样检查。 |
| 暴力破解 | 访问密码：每个 IP 5 次，另有全局监控并告警。<br>登录 / 恢复：按账号和按 IP 分别计数，一小时内上限。<br>两步验证：按账号计算失败上限并告警。 |
| 防刷（v0.7） | 每个会话 API 请求：突发 600 次，之后每秒 20 次（每个 IP 另有 3 倍的总上限）。<br>每个用户发消息：突发 120 条，之后每秒 2 条。<br>每个用户的 WebSocket 事件（所有连接合计）：突发 300 个，之后每秒 60 个。<br>错误报告：每个 IP 每小时 30 条，全站每分钟 60 条。<br>超出时返回「请稍后再试」，客户端会自动等待重试。 |
| CSRF | 所有非 GET 请求检查 Origin；Cookie SameSite。 |
| 安全响应头 | CSP：只允许本站脚本，禁止 iframe、object 和外部连接。<br>另有 HSTS、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、COOP、CORP same-origin、`nosniff`。<br>Permissions-Policy 只开放摄像头、麦克风、屏幕共享、通行密钥。 |
| 链接预览 | 默认关闭。服务器代取网页时防 SSRF：禁止内网地址，逐跳检查重定向，限制大小和时间。 |
| 端口 | Node 只监听 127.0.0.1:3000（v0.7 起这也是默认值），由 Nginx 反向代理。 |
| 进程 | systemd 以网站用户运行，开启 NoNewPrivileges、ProtectSystem 等限制。 |
| 运维脚本（v0.7） | 以 root 运行的脚本（每日备份、升级、日志上限）放在 root 专有的 `/usr/local/lib/securechat-ops/`，网站用户改不了。v1.0 起：root 不执行网站目录里的任何代码（`npm ci`、读取数据库、读版本号都以 `www` 身份进行），往网站目录写文件也以 `www` 身份进行，只选用属于 root、别人改不了的 Node.js。每次升级自动运行服务器自检（`doctor.sh`）。 |
| 数据保留 | 访问日志和已处理的准入申请默认保留 90 天（`LOG_RETENTION_DAYS`），管理操作记录 1 年，错误报告 90 天。 |
| 依赖 | 每个版本发布前运行 `npm audit`（v0.7.0：0 个已知漏洞）。 |

## 8. 已知限制

1. **网页代码由服务器提供。** 控制了服务器的人可以下发恶意代码。缓解措施：
   - **发布签名（v0.9）**：
     - 更新包由开发者的发布密钥（Ed25519）签名。服务器上的 `update.sh` 先把包复制到 root 专有目录，再用 root 手动固定的公钥检查签名，不通过就不安装，也不接受比当前版本旧的包。
     - 网页代码指纹同样签名，页面和 `status.sh` 都会检查。
     - 这堵住了「借升级换代码」和「偷换磁盘上的网页文件」两条路。但已经控制了运行中 Node 进程的人，仍然可以改写返回给浏览器的内容。
   - **网页代码指纹（v0.8）**：每个更新说明里都写着这个版本的指纹。设置 → 安全里显示页面自己算出的指纹；代码在版本号没变的情况下变了，页面会提醒。但被恶意替换的代码也能伪造这个显示，所以它只能发现粗糙或意外的改动。
   - **服务器上核对**：root 执行 `status.sh`（或 `node ops/fingerprint.mjs`）会从磁盘上的网页文件重新计算指纹。它只覆盖网页文件：控制了 Node 服务的人不用改这些文件，也能改写服务器返回的内容。
   - 更根本的办法（打包成 App，或用浏览器扩展校验代码）还没有做。
2. **普通聊天没有前向保密。** 一个账号的身份私钥如果泄露（比如设备被控制），攻击者可以解开这个账号在普通聊天里能看到的全部历史消息。
   - 缓解：群密钥定期更换，移除成员立即换钥；阅后即焚的消息到期后服务器会删除。
   - 需要前向保密时用「私密对话」（v0.8）。代价是只能在两台设备上用、没有云端历史，详见 [前向保密设计](前向保密设计.md)。
3. **元数据可见**，见[第 4 节](#4-服务器能看到什么)。v0.9 减少了一些（附件大小分档、可选模糊在线状态、可选推送延迟合并），但谁和谁在什么时候通信，服务器仍然知道；「正在输入」和已读回执也是实时的。
4. **所有设备共用一套身份密钥。** 一台设备泄露就等于账号泄露，处理方法是在其他设备上让它下线并重置恢复词。
5. **群通话是两两直连**（最多 6–8 人），各成员之间能看到彼此的 IP，除非开启「只走中转」。
6. **发布私钥的保管**：发布私钥在开发者的电脑上。它一旦泄露，攻击者就能签出服务器会接受的更新包，直到 root 用 `install-release-key.sh --replace` 换成新公钥为止。
7. **没有经过独立的第三方安全审计。** 每个版本发布前都做内部代码审查、自动化测试和依赖漏洞扫描。
