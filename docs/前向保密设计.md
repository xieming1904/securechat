# 前向保密（Forward Secrecy）设计评估

> 状态：**方案 A（私密对话）已在 v0.8 实现**。第 4 节已按实际实现更新，和最初设计不同的地方都注明了。
> 背景见[安全设计](安全设计.md)的「已知限制」第 2 条。

## 1. 问题

现在的加密方式：

- 每个聊天有一把聊天密钥，按纪元更换。
- 聊天密钥用每个成员**长期不变**的 X25519 公钥封装，保存在服务器上。
- 所有纪元的封装密钥都留在服务器，这样换设备、在新设备登录后还能读历史消息。

后果：如果某个账号的身份私钥泄露（设备被木马控制、浏览器配置被拷走），攻击者再拿到服务器上的密文（服务器被入侵、备份泄露），就能解开**这个账号参与过的全部历史消息**。

「前向保密」要求的是：**今天密钥泄露，不影响昨天的消息。**

## 2. 根本矛盾

前向保密和密聊现在的两个功能是冲突的：

| 现有功能 | 需要什么 | 和前向保密的关系 |
|---|---|---|
| 换设备、新设备登录后还能看到全部历史 | 用长期密钥（密码或恢复词）随时能重新解开旧消息 | **直接冲突**：能随时解开，就意味着长期密钥泄露时也能解开 |
| 多设备同时在线，共用一套身份密钥 | 所有设备都持有同一把私钥 | 一台设备泄露，就等于所有设备泄露 |
| 服务器保存全部密文历史 | 密文长期存在 | 本身不冲突，但会放大上面两点 |

Signal 能做到前向保密，是因为它不在服务器保存历史：换手机时历史要么丢掉，要么靠本地迁移。Telegram 的做法是分成两种：普通聊天（云端，没有前向保密）和**私密聊天**（绑定设备，有前向保密）。

**结论**：不能在不牺牲「新设备看历史」的前提下，给所有聊天都加上前向保密。可行的做法是新增一种聊天类型，由用户选择。

## 3. 方案比较

| 方案 | 做法 | 优点 | 缺点 | 评估 |
|---|---|---|---|---|
| A. 私密对话（推荐） | 一对一、绑定设备，使用 X3DH 建立会话 + Double Ratchet（双棘轮），服务器只暂存到送达为止 | 成熟协议（Signal 公开规范），能做到前向保密和「被攻破后自愈」；不影响现有聊天 | 不能多设备同步；换设备看不到历史；不支持群 | **v0.8 实现** |
| B. 群组用 MLS（RFC 9420） | 树形密钥协商，所有成员共同推进纪元 | 群组级别的前向保密和自愈 | 浏览器里没有成熟的 JS 实现（OpenMLS 需要编译成 wasm），和签名成员链要重新设计，工作量很大 | 暂不做，继续跟踪 |
| C. 群组 Sender Keys + 定期删旧钥 | 每人一条发送链，按消息推进；旧链密钥在本机删除 | 比 MLS 简单 | 多设备、新成员看历史仍然冲突；成员移除时要全员重建 | 作为 v0.9 以后的候选 |
| D. 只缩短普通聊天的换钥周期 | 7 天 / 1000 条 → 1 天 / 200 条 | 几乎不用改 | 旧密钥仍然存在服务器上，**不是**前向保密，只是限制了单把密钥的使用量 | 不采用（没有实际意义） |

## 4. 推荐方案 A：私密对话

### 4.1 用户看到的样子

- 在联系人信息页选「发起私密对话」，列表里显示单独的锁形图标。
- 只在**发起和接受的这两台设备**上存在，你的其他设备上完全看不到这个对话。（原设计里「其他设备显示『私密对话在另一台设备上』」没有实现，因为那需要让服务器知道谁有私密对话。）
- 发起时会邀请对方的**所有**设备，第一台上线的设备自动接受；对方其他设备随后会收到「已在另一台设备上接受」。
- 不能转发、不能导出，不进本机搜索缓存；默认开启阅后即焚（1 天，可以改或关闭），每条消息按发送方的设置计时。
- 双方设备都显示安全码，可以核对。
- 换设备、清除浏览器数据后，私密对话就没有了（和 Telegram 一样）。

### 4.2 密钥

每台设备单独生成，**不复用**账号的身份密钥：

| 密钥 | 类型 | 生命周期 |
|---|---|---|
| 设备身份密钥 | X25519，由账号的 Ed25519 身份密钥签名（证明这台设备属于这个账号） | 设备存在期间 |
| 签名预密钥（SPK） | X25519，由设备身份签名 | 每 7 天更换，旧的保留到 14 天后删除 |
| 一次性预密钥（OPK） | X25519，一次上传 50 个 | 用一个删一个，少于 20 个时自动补充；服务器发出后 30 天没被用上的，私钥也删除 |

服务器只保存公钥部分：`devices`（设备证书、当前签名预密钥，绑定到登录会话）和 `device_opks`（一次性预密钥）。注册设备时还要用设备私钥签一次名，证明这个会话确实持有设备密钥，防止同一账号的其他会话把设备的收件队列转走。

### 4.3 建立会话（X3DH）

按 Signal 的 X3DH 规范：

1. 发起方从服务器取对方设备的预密钥包，并验证签名链：账号 Ed25519 → 设备身份 → SPK。
2. 生成临时密钥 EK，计算 DH1 = DH(IK_A, SPK_B)、DH2 = DH(EK_A, IK_B)、DH3 = DH(EK_A, SPK_B)、DH4 = DH(EK_A, OPK_B)（有 OPK 时）。
3. 共享密钥 SK = KDF(DH1 ‖ DH2 ‖ DH3 ‖ DH4)，用来初始化双棘轮。
4. 服务器发出的 OPK 用过即删；同一个 OPK 被第二次使用时，接收方拒绝。

用到的 libsodium 原语：`crypto_scalarmult`（X25519），`crypto_generichash`（BLAKE2b，作 HKDF），`crypto_aead_xchacha20poly1305_ietf`，`crypto_sign`（Ed25519）。不引入新的密码学库。

### 4.4 双棘轮（Double Ratchet）

按 Signal 的 Double Ratchet 规范：

- **对称棘轮**：每条消息推进一次链密钥，消息密钥用完即删 → 前向保密。
- **DH 棘轮**：每次对方回复时换一对新的 X25519 密钥 → 被攻破后，下一轮往返就能恢复安全（自愈）。
- 乱序消息：每条链最多跳过 1000 条，总共最多缓存 2000 个跳过的消息密钥，超过 7 天删除。
- 消息头（DH 公钥、链序号）也加密（header encryption），服务器看不到对方的棘轮进度。
- 棘轮状态存在 IndexedDB，用本机不可导出的 AES-GCM 密钥加密。

### 4.5 服务器

- 新表 `secret_envelopes(id, to_device, from_device, from_user, ct, created_at)`：只作为投递队列，目标设备确认收到后**立即删除**，最长保留 14 天。每个发送方对每台目标设备最多排队 300 条，每条最大 100 KB。
- 不写入 `messages` 表，没有 seq，也不进入历史。
- 服务器能看到的元数据和普通私聊一样（谁和谁、什么时候、多大）。

### 4.6 各种情况的处理

| 情况 | 处理 |
|---|---|
| 对方换了设备或清除了数据 | v0.9：打开对话或发送失败时会发现对方设备已不存在，明确提示并提供「重新发起」。新对话需要重新核对安全码 |
| 对方的账号密钥变了（安全码变更） | 在重新核对安全码之前，拒绝发起和接受私密对话（防止服务器冒充） |
| 这台设备退出登录或被远程下线 | 服务器删除这台设备和它的队列；本机删除所有私密对话的密钥和消息 |
| 被屏蔽 / 注销账号 | 同普通聊天：服务器拒绝投递 |
| 附件 | 文件用一次性随机密钥加密，上传到两人私聊所在的位置，文件密钥放在棘轮消息里。服务器上的加密文件固定保留 14 天后删除（不跟阅后即焚同步）；到期后本机的密钥也会删除 |
| 通话 | v0.9 起可以。发起方为每次通话生成一把随机信令密钥，和邀请一起经双棘轮送到对方那台设备；之后的信令用这把密钥加密。只有这两台设备响铃，通话记录只留在本机。媒体是 DTLS-SRTP（临时密钥） |

### 4.7 能保证与不能保证

| 能 | 不能 |
|---|---|
| 设备今天被攻破，不能解开之前已经删掉消息密钥的消息 | 设备被攻破期间，攻击者能看到当时屏幕上和本机还保存着的消息（没到期的阅后即焚消息、没开阅后即焚的全部消息） |
| 攻击者只拿到一次设备密钥时，一轮往返后会自愈 | 服务器仍然看得到元数据 |
| 服务器和数据库泄露也解不开，而且历史密文本来就不保存 | 网页代码仍然由服务器提供（见安全设计第 8 节第 1 条） |

## 5. 测试（v0.8 实际完成）

- 协议单元测试（`server/test/ratchet.test.ts`）：设备证书和签名预密钥校验、乱序、跨链的迟到消息、篡改头部/正文/关联数据、重放、跳过上限、低阶点、状态存储往返。
- 对照测试：另写了一份按规范伪代码结构的参考实现（`ratchet-ref.ts`），用同一个确定性随机源驱动，双棘轮部分的密文逐字节一致（X3DH 部分的 DH 顺序按规范，两边共用）。
- 服务器测试：证书和绑定签名校验、OPK 只发一次、陌生人拿不到预密钥、只有目标设备能读和确认、屏蔽后拒绝、退出登录后设备和队列一起删除。
- 端到端测试：三台「鲍勃」设备中只有一台接到对话；双向收发、附件、双方安全码一致、30 秒阅后即焚、刷新后继续、结束后双方删除；爱丽丝的另一台设备看不到。
- 发布前做了一次专门的密码学审查：协议核心没有发现问题；发现的周边问题（安全码变更时仍可发起、接受消息丢失、退出登录后残留等）都已修复。仍然建议找第三方审计。

## 6. 暂不做的

- **群组前向保密**（MLS / Sender Keys）：等私密对话稳定后，看浏览器里的 MLS 实现是否成熟再评估。
- **普通聊天改用前向保密**：和「新设备看历史」冲突，不做。普通聊天继续依靠定期换钥、移除成员时立即换钥、阅后即焚。
