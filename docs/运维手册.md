## 1. 日常速查

程序由系统服务 `securechat` 托管：崩溃后 3 秒内自动拉起，服务器重启后自动启动。

以下命令都在宝塔「终端」里用 root 执行。

> **v0.7 起**，运维脚本另有一份放在只有 root 能改的 `/usr/local/lib/securechat-ops/`（每次升级自动更新），每日备份也从那里运行。原因是网站目录属于 `www` 用户，宝塔上的其他网站也以 `www` 运行，理论上可能改动网站目录里的脚本，再借 root 执行。**以 root 执行运维命令时，一律用 `/usr/local/lib/securechat-ops/` 下的脚本**（v0.9 起升级也是），下表中的 `/www/wwwroot/securechat/ops/` 都可以直接替换成它。


| 做什么 | 命令 |
|---|---|
| 查看状态（版本、网页代码指纹、备份、磁盘、异地备份） | `bash /www/wwwroot/securechat/ops/status.sh` |
| **服务器自检，缺什么装什么**（v1.0） | `bash /usr/local/lib/securechat-ops/doctor.sh`（只看不改：加 `--check`），见[第 2 节「自检」](#自检v10) |
| 重启 / 停止 / 启动 | `systemctl restart securechat`（stop / start 同理） |
| 看最近日志 | `journalctl -u securechat -n 100` |
| 立即备份一次 | `bash /www/wwwroot/securechat/ops/backup.sh` |
| 恢复演练（不影响线上） | `bash /www/wwwroot/securechat/ops/restore-drill.sh` |
| 升级 | 见[第 2 节](#2-升级) |
| 关闭某人的两步验证 | `bash /www/wwwroot/securechat/ops/reset-2fa.sh 用户名` |
| 把自己的 IP 加回白名单 | 见[第 7 节](#7-排错) |
| 限制系统日志大小（500 MB / 30 天） | `bash /usr/local/lib/securechat-ops/log-limits.sh`（v0.7 起升级时自动执行） |
| 临时打开逐条请求日志（排错用） | `.env` 里加 `LOG_REQUESTS=1` 后重启；用完删掉再重启 |

**宝塔面板里的注意事项：**

- 「Node 项目」里 securechat 显示「未启动」是正常的，**不要在面板里点启动**。
- 这个项目条目要保留，不要删除（Nginx 和 SSL 配置挂在它下面）。
- **端口 3000 只监听本机**（`HOST=127.0.0.1`），**不要在防火墙或阿里云安全组里放行 3000**。

管理后台（网页右上角菜单 → 管理后台）可以看到：

- 用户、IP 白名单和准入申请
- 统计、告警和操作记录
- 「备份」页：本地备份和异地备份最近一次的时间
- 「错误日志」页（v0.7）：用户浏览器里发生的意外错误。
  - 匿名：不记录账号和 IP，也不含聊天内容。
  - 相同的错误合并显示；点一行可以看代码位置。
  - 升级后如果某个错误突然变多，把这一页的内容发给开发者。

## 2. 升级

从 v0.9 起，每个更新包都带一个**签名文件**（`.sig`）。服务器只安装用发布密钥签过名的包。

1. 在宝塔「文件」里把**两个文件**上传到 `/www/wwwroot/`：
   - 更新包，例如 `securechat-update-v0.9.0.tar.gz`；
   - 签名文件，例如 `securechat-update-v0.9.0.tar.gz.sig`。
2. 执行（注意是 **root 专有目录**里的脚本）：
   ```bash
   bash /usr/local/lib/securechat-ops/update.sh /www/wwwroot/securechat-update-v0.9.0.tar.gz
   ```
3. 执行 `bash /usr/local/lib/securechat-ops/status.sh`，确认两点：
   - 版本号是新版本；
   - 「网页代码指纹」和更新说明里写的一致，后面显示「✔ 已由发布密钥签名」。
4. 浏览器刷新一次（旧缓存会自动清理）。

`update.sh` 会依次做这些事：

0. **服务器自检**（v1.0 起）：检查升级要用的工具、Node.js 22 和磁盘空间，缺的自动安装。装不上就停止，这时程序和数据都还没动；
1. 把更新包和签名文件复制到只有 root 能访问的临时目录，之后只用这份副本（防止有人在检查之后偷换文件）；
2. 用已固定的发布公钥检查签名，不通过就停止；
3. 拒绝比当前版本旧的包（防止有人用旧的、有已知问题的正式包「降级」）；
4. 备份数据；
5. 保存当前代码，保留最近 5 个版本，放在 `/www/backup/securechat-releases/`；
6. 安装新版：依赖有变化时自动执行 `npm ci`（以 www 身份，大约 1 分钟；只改版本号不算变化）；然后对新版本再自检一次（依赖、配置和权限、系统服务、root 专有脚本、可选组件），缺的补上，补不上就回滚；
7. 迁移数据库：只新增，不改动旧数据；
8. 重启，并确认新版本已经启动；
9. 更新 root 专有的运维脚本副本，记录已安装的版本，检查系统日志上限；最后检查运行状态（服务、端口只监听本机、健康检查）。

新版本 30 秒内没起来会**自动回滚**（运维脚本也一起回到旧版本）。

每个新版本的更新包都包含之前所有版本的内容，**只需要上传最新的那一个**（和它的 `.sig`）。

### 发布公钥（v0.9 起）

服务器用 `/usr/local/lib/securechat-ops/release.pub` 检查签名。这个文件**不会被任何更新自动安装或替换**，只能由 root 手动固定：

```bash
bash /usr/local/lib/securechat-ops/install-release-key.sh /www/wwwroot/securechat/ops/release.pub "3DCD B3B5 A9C3 3336"
```

- 最后那串是**密钥 ID**，每个版本的更新说明里都会写。脚本会先算出文件里公钥的 ID，和你输入的比对，一致才安装。
- 请以开发者直接发给你的更新说明为准，不要相信服务器上某个文件里写的 ID。
- 还没有固定公钥时，`update.sh` 会拒绝更新。确认更新包来源可靠时，可以临时用 `ALLOW_UNSIGNED=1 bash …/update.sh …` 跳过检查。

**更换发布密钥**（只有开发者明确通知换了密钥时才做）：

```bash
bash /usr/local/lib/securechat-ops/install-release-key.sh <新的 release.pub> "<新的密钥 ID>" --replace
```

- 如果旧的发布私钥丢了或者泄露了，开发者会生成新密钥，并在更新说明里给出新的密钥 ID。
- 在固定新公钥之前，旧密钥签的包仍然会被接受。所以密钥一旦泄露，要尽快换。

### 自检（v1.0）

`doctor.sh` 检查密聊在这台服务器上需要的所有东西，**缺什么装什么，能修的自动修**。每次升级都会自动运行，平时也可以手动运行：

```bash
bash /usr/local/lib/securechat-ops/doctor.sh           # 检查并修复
bash /usr/local/lib/securechat-ops/doctor.sh --check   # 只检查，不改动任何东西
```

每一行前面的符号：✔ 正常 · ➜ 刚刚修好 · ⚠ 提醒（不影响使用）· ✘ 需要人来处理。只要有 ✘，脚本就返回失败。

| 检查项 | 缺了或不对时自动做什么 |
|---|---|
| 系统工具 curl、rsync、tar、sha256sum、ss | 用系统包管理器（apt / dnf / yum）安装 |
| Node.js 22 | 依次找宝塔装的、之前自检装的、系统里的。都没有时，从 nodejs.org 下载官方版本，装到 `/usr/local/lib/securechat-node`。校验和一律从 nodejs.org 取，下载慢时安装包可以从国内镜像取，校验不通过就丢弃。连不上 nodejs.org 就不装，请在宝塔「Node.js 版本管理器」里装 v22 |
| 服务器依赖 | 每个依赖都要能加载，数据库原生模块要和当前 Node 匹配；不满足就以 www 身份重新 `npm ci`（日志在 `/var/log/securechat/npm.log`） |
| `.env` | 必须存在，并且有 `OPAQUE_SERVER_SETUP`。**登录密钥永远不会自动生成**（生成新的会让所有人都登录不了），丢了请从 `/root/securechat-env.backup` 恢复。权限改回 600；`HOST` 不是 127.0.0.1 就改回来；备份到 `/root/securechat-env.backup` |
| 数据目录 | 权限改回 700、属主 www |
| 磁盘 | 剩余少于 1 GB 时报 ✘（不会自动删东西） |
| 系统服务、每日备份定时器 | 配置和当前版本不一致就重写；没开机自启、定时器没开就打开 |
| root 专有运维脚本 | 属主不是 root 就改回来。发布公钥没固定时只提醒，因为固定前要你核对密钥 ID |
| 异地备份（开了才查） | 缺 gpg、rclone 就安装 |
| TURN 中转（配了才查） | coturn 没运行就重启 |
| 运行状态 | 服务是否运行、端口 3000 是否只监听本机、健康检查 |

自检**不会**做的事：生成或替换密钥、固定发布公钥、改防火墙和安全组、删除任何文件。

v1.0 起，root 不执行网站目录里的任何代码：`npm ci`、依赖检查、往网站目录复制新文件都以 `www` 身份进行，root 只使用属于 root、别人改不了的 Node.js。如果宝塔装的 Node.js 目录别人能改，自检会提示「忽略了 …」，改用自己安装的那一份。

### 特殊情况

| 情况 | 做法 |
|---|---|
| 确实要回到旧版本 | `ALLOW_DOWNGRADE=1 bash /usr/local/lib/securechat-ops/update.sh <旧版本的包>` |
| 想以 root 执行 `install-service.sh`、`doctor.sh` | v1.0 起，从网站目录启动也会自动改用 `/usr/local/lib/securechat-ops/` 里的那份 |
| 从网站目录里运行了 `update.sh` | 如果 root 专有目录里已经有 `update.sh`，脚本会自动改用那一份。网站目录属于 `www` 用户，里面的脚本可能被改过，请始终用 `/usr/local/lib/securechat-ops/` 下的脚本。 |

## 3. 备份与恢复

### 本地备份（自动）

- 每天 04:17 左右自动备份到 `/www/backup/securechat/`，保留最近 7 天。
- 内容是数据库快照和附件（都是密文）。附件用硬链接存，没变化的文件不重复占空间。
- 登录密钥文件 `.env` 另存为 `/root/securechat-env.backup`，只有 root 可读。**没有这个文件，恢复备份后所有人都无法登录。**
- 管理后台「备份」页会显示最近一次备份的时间和大小；超过 36 小时没有成功备份会告警。

### 异地备份（强烈建议开启）

本地备份和网站在同一台服务器上，服务器整体损坏时会一起丢失。开启异地备份后，每天的备份会先用 gpg（AES-256）加密，再用 rclone 上传到阿里云 OSS；OSS 上只有密文。

**第一次设置（AccessKey 由你自己输入，脚本不会接触到它）：**

1. 在阿里云建一个私有 OSS 存储桶（建议选香港地域）。
2. 在 RAM 里建一个子账号，只给它这个存储桶的读写权限，记下它的 AccessKey。
3. 在宝塔终端执行 `rclone config`，新建一个远端，按提示填写：
   - 名字：`oss`
   - 类型：`s3`
   - provider：`Alibaba`
   - AccessKey：填入上一步记下的 ID 和 Secret
   - endpoint：选 `oss-cn-hongkong.aliyuncs.com`
   - 其余直接回车用默认值
4. 执行下面的命令（`30` 是异地备份的保留天数）：
   ```bash
   bash /www/wwwroot/securechat/ops/setup-offsite.sh oss:存储桶名/securechat 30
   ```
5. **把 `/root/securechat-offsite.key` 另外保存一份**，比如存到密码管理器。没有它，就解不开异地备份。

之后每天会自动上传。上传失败或超过 48 小时没有上传成功时，后台会告警。

解密一份异地备份：
```bash
gpg --batch --pinentry-mode loopback --passphrase-file /root/securechat-offsite.key -d securechat-<日期>.tar.gpg | tar xf -
```

### 从备份恢复（真出事时）

```bash
systemctl stop securechat
cd /www/wwwroot/securechat
mv data data.broken-$(date +%F)                 # 旧数据先挪开，不删
cp -a /www/backup/securechat/<日期目录> data      # 选一份备份
chown -R www:www data && chmod 700 data
cp /root/securechat-env.backup .env && chown www:www .env && chmod 600 .env   # 仅当 .env 也丢了
systemctl start securechat && bash ops/status.sh
```

恢复之前请注意：

- 恢复到哪一天的备份，那之后的消息就会丢失。
- 已经「为双方删除」的消息，如果还在备份期内，会随备份一起回来（7 天后会自动轮换掉）。

建议每个月执行一次 `ops/restore-drill.sh`。它会检查备份能不能用，而且不影响线上。

## 4. 账号与安全操作

| 场景 | 怎么做 |
|---|---|
| 邀请新用户 | 管理后台 → 注册邀请 → 生成链接或短码 |
| 停用某个账号 | 管理后台 → 用户 → 停用（这个人所有设备立即下线；以后可以再启用） |
| 用户想注销自己的账号 | 让他自己在「设置 → 安全 → 注销账号」里操作。管理员不能替别人注销。 |
| 有人丢了验证器 / 通行密钥，恢复码也没了 | 先当面或电话核实确实是本人，再执行 `bash /www/wwwroot/securechat/ops/reset-2fa.sh 用户名` |
| 要求所有人开启两步验证 | 管理后台 → 系统设置 →「要求所有人开启两步验证」（管理员自己要先开启） |
| 怀疑有人在猜密码 | 看「告警」页：密码错误、两步验证失败次数过多时都会告警 |
| 紧急情况：暂时只放行白名单 | 管理后台 → 系统设置 → 紧急锁定 |

**关于注销（v0.6）：**

- 注销后，这个人的密码、恢复词、两步验证、个人数据和头像全部删除。
- 他已经发出的消息在别人那里保留，名字显示为「已注销账号」。
- 用户名永久保留，不能被别人重新注册。
- 他创建的邀请会作废。
- 如果注销的是唯一的管理员，系统会拒绝，要先把另一个人设为管理员。

**`reset-2fa.sh`** 故意只能在服务器上用 root 执行，网页后台做不了。这样即使管理员账号被盗，攻击者也没法关掉别人的两步验证。

## 5. 可选组件

### TURN 中转（让不同网络之间的通话更容易接通）

```bash
bash /www/wwwroot/securechat/ops/install-coturn.sh chat.example.com
```

装好后，在阿里云安全组和宝塔「安全」里放行：`3478/udp`、`3478/tcp`、`5349/tcp`、`49160-49200/udp`。
通话内容始终端到端加密，中转服务器只转发密文。

群通话是每个人两两直连，走中转时流量会经过这台服务器。人数上限：语音 8 人，视频 6 人。

### 固定网站地址（通行密钥用）

在 `.env` 里加一行 `PUBLIC_ORIGIN=https://chat.example.com`，然后执行 `systemctl restart securechat`。
加上以后，通行密钥只和正式网址绑定，从其他地址（比如直接用 IP 访问）打开时不能使用。

### 检查更新提示

在 `.env` 里设置 `UPDATE_FEED_URL=<一个 JSON 地址>`，后台会提示有没有新版本。
这只是提示：升级仍然要手动执行 `update.sh`。

## 6. 配置项（.env）

文件位置 `/www/wwwroot/securechat/.env`，权限 600，属主 www。改完执行 `systemctl restart securechat`。

| 变量 | 含义 | 说明 |
|---|---|---|
| `PORT` | 监听端口 | 3000 |
| `HOST` | 监听地址 | **必须是 127.0.0.1** |
| `TRUST_PROXY` | 信任哪个反向代理传来的真实 IP | `loopback`（本机的 Nginx） |
| `PUBLIC_ORIGIN` | 正式网址 | 用于生成邀请链接、固定通行密钥 |
| `OPAQUE_SERVER_SETUP` | 登录密钥 | **生成之后永远不要改**，改了所有人都无法登录；不要和数据备份放在一起 |
| `TURN_URLS` / `TURN_SECRET` | 通话中转 | 由 `install-coturn.sh` 自动写入 |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | 推送密钥 | 不设置会自动生成，并保存在数据库里 |
| `UPDATE_FEED_URL` | 更新提示 | 可选 |
| `LOG_RETENTION_DAYS` | 访问验证日志、已处理的准入申请保留几天 | 默认 90（v0.7） |
| `LOG_REQUESTS` | 设为 `1` 时逐条记录请求（含访问者 IP） | 默认关闭，只在排错时临时打开（v0.7） |
| `API_BURST` / `API_PER_SEC` | 每个会话的 API 请求上限：突发次数 / 每秒恢复 | 默认 600 / 20，一般不用改（v0.7） |

运维脚本的设置（异地备份目标、保留天数）保存在 `/etc/securechat-ops.conf`。

## 7. 排错

| 现象 | 处理 |
|---|---|
| 自己打开网站只看到「访问验证」页 | 如果 IP 变了，输入访问密码即可；或者在终端执行下面的「放行 IP」命令 |
| 后台白名单里显示 127.0.0.1 | Nginx 没有传真实 IP。检查站点配置里有没有 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` |
| 网站打不开（502） | 先执行 `systemctl status securechat`，再看 `journalctl -u securechat -n 100` |
| 升级时停在「服务器自检」 | 看上面带 ✘ 的行，按提示处理后重新执行升级命令。最常见的是服务器连不上 nodejs.org 或 npm 源 |
| 不确定服务器缺不缺东西 | `bash /usr/local/lib/securechat-ops/doctor.sh --check` |
| 升级后网站异常 | 升级本来会自动回滚；如果还有问题，把 `/www/backup/securechat-releases/` 里的上一个版本解压回去，再重启 |
| 通话接不通 | 双方在不同网络时需要 TURN 中转，见[第 5 节](#5-可选组件) |
| 通行密钥提示「需要通过 https 网址打开」 | 必须用正式的 https 域名访问，不能用 IP |
| 大文件上传失败 | 检查站点配置：`client_max_body_size 110m;` 和 `proxy_request_buffering off;` |
| 磁盘告警 | 执行 `ops/status.sh` 看占用；可以在后台设置「附件保留天数」，自动清理旧附件；执行 `ops/log-limits.sh` 限制系统日志 |
| 有人反映「请求太频繁，请稍后再试」 | 这是 v0.7 加的防刷上限，正常使用碰不到。如果确实是正常使用，可以在 `.env` 里调大 `API_BURST` / `API_PER_SEC` |
| 某个功能在用户那里报错，但你这里复现不了 | 看管理后台「错误日志」 |
| `status.sh` 显示「与更新包自带的指纹不一致」，或用户反映页面提示「网页代码在版本号没变的情况下发生了变化」 | 网页文件在升级之后被改动过。先确认最近没有人手动改过 `web/dist`；如果没有，服务器可能被入侵：重新上传官方更新包再执行一次升级，并检查服务器 |

放行 IP、再要一个管理员邀请：
```bash
cd /www/wwwroot/securechat && set -a; . ./.env; set +a
sudo -u www env DATA_DIR=$PWD/data node server/dist/scripts/allow-ip.js <你的IP>
sudo -u www env DATA_DIR=$PWD/data OPAQUE_SERVER_SETUP="$OPAQUE_SERVER_SETUP" node server/dist/scripts/init.js --admin-invite --origin "$PUBLIC_ORIGIN"
```

## 8. 从零部署

只有换服务器时才需要。当前服务器已经部署好了，平时用不到这一节。

1. **Node.js 22**：宝塔 → 软件商店 →「Node.js 版本管理器」→ 安装 v22.x，并设为命令行版本。
2. **上传并解压**：把部署包 `securechat-deploy.tar.gz` 解压到 `/www/wwwroot/securechat`。
3. **依赖和密钥**（在宝塔终端执行）：
   ```bash
   cd /www/wwwroot/securechat
   npm ci --omit=dev -w server
   cat > .env <<EOF
   PORT=3000
   HOST=127.0.0.1
   TRUST_PROXY=loopback
   PUBLIC_ORIGIN=https://chat.你的域名.com
   OPAQUE_SERVER_SETUP=$(node -e "import('@serenity-kit/opaque').then(async o=>{await o.ready;console.log(o.server.createSetup())})")
   EOF
   chmod 600 .env && mkdir -p data && chmod 700 data && chown -R www:www /www/wwwroot/securechat
   ```
4. **Node 项目**：宝塔 → 网站 → Node 项目 → 添加。
   - 项目目录：`/www/wwwroot/securechat`
   - 启动命令：`bash /www/wwwroot/securechat/start.sh`
   - 端口：3000
   - 运行用户：www
   - 绑定域名：你的域名
5. **Nginx**：在站点配置里确认有下面这些设置：
   ```nginx
   client_max_body_size 110m;
   location / {
       proxy_pass http://127.0.0.1:3000;
       proxy_http_version 1.1;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
       proxy_set_header X-Forwarded-Proto $scheme;
       proxy_set_header Upgrade $http_upgrade;
       proxy_set_header Connection "upgrade";
       proxy_read_timeout 3600s;
       proxy_request_buffering off;
   }
   ```
6. **HTTPS**：站点 → SSL → Let's Encrypt，然后打开「强制 HTTPS」。这一步是必须的：加密接口、推送、通行密钥都要求 HTTPS。
7. **系统服务和每日备份**：
   ```bash
   bash /www/wwwroot/securechat/ops/install-service.sh
   bash /usr/local/lib/securechat-ops/doctor.sh
   ```
   第二条是自检（v1.0），补齐缺的东西，最后应该没有 ✘。
8. **初始化**（设置访问密码，并生成管理员注册链接）：
   ```bash
   cd /www/wwwroot/securechat && set -a; . ./.env; set +a
   sudo -u www env DATA_DIR=$PWD/data OPAQUE_SERVER_SETUP="$OPAQUE_SERVER_SETUP" \
     node server/dist/scripts/init.js --password '至少8位的访问密码' --origin "$PUBLIC_ORIGIN"
   ```
   打开输出的「管理员注册链接」注册管理员。链接 24 小时内有效，只能用一次。
9. **检查**：
   - 用没放行的网络（比如手机流量）打开网站，应该只能看到「访问验证」页；
   - 后台 IP 白名单里应该显示你的真实公网 IP。

## 9. 容量与压力测试

压力测试脚本在开发机上运行。不要在线上服务器运行，它会自己启动一个临时的测试服务器。

```bash
npm run loadtest -w server -- 100 45 2000    # 100 人、45 秒、每人约 2 秒发一条
```

测试场景（v0.9 起群上限是 100 人）：

- 100 个用户同时在线，建一个 100 人群，外加 100 个私聊；
- 每人每 1–3 秒发一条消息，60% 发到大群（每条要推送给 99 个人）。

开发机上的结果（2 核虚拟机；客户端和服务器跑在同一个进程里，所以实际服务器负载比这更低）：

| 指标 | 50 人（v0.7） | 100 人（v0.9） |
|---|---|---|
| 发送量 | 约 25 条/秒，没有错误 | 约 50 条/秒，没有错误 |
| 发送耗时（HTTP） | 中位数 3 ms，95% ≤ 7 ms | 中位数 4 ms，95% ≤ 8 ms |
| 送达耗时（实时推送） | 中位数 4 ms，95% ≤ 10 ms | 中位数 6 ms，95% ≤ 12 ms |
| 读取 50 条历史（所有人同时读） | 约 60 ms | 约 110 ms |
| CPU | 一个核的 15% | 一个核的 31% |
| 内存 | 约 250 MB | 约 260 MB |

结论：这台 2 核服务器支撑 100 人同时活跃没有压力。瓶颈更可能在带宽，比如群视频通话走 TURN 中转时。群通话的人数上限不变：语音 8 人，视频 6 人。

## 10. 安全须知

完整的威胁模型、加密方式和服务器能看到的数据，见[安全设计](安全设计.md)。私密对话（前向保密）的设计和实现见[前向保密设计](前向保密设计.md)。

- **服务器看不到：** 消息内容、附件、头像、群名、备注、收藏。它们都在浏览器里加密。
- **服务器能看到的元数据：**
  - 谁和谁在一个聊天里、什么时候发的消息、附件多大；
  - 谁在通话里；
  - 谁对哪个聊天开了免打扰（为了跳过推送）；
  - 登录 IP；访问验证日志里的 IP（默认保留 90 天）。
- **服务器日志（v0.7 起）：** 默认不逐条记录请求，只记录错误；系统日志最多 500 MB / 30 天。
- **管理员的权限：** 管理员能停用账号、管理白名单，但**读不到任何人的消息**，也关不掉别人的两步验证（只有服务器 root 能关）。
- **最敏感的三样东西要分开保存：**
  - `.env`（尤其是其中的 `OPAQUE_SERVER_SETUP`）；
  - `/root/securechat-env.backup`；
  - `/root/securechat-offsite.key`。
- **尚未经过独立安全审查。** 每个版本发布前都做过内部的代码安全审查和自动化测试，但独立的第三方审计还没有做。
